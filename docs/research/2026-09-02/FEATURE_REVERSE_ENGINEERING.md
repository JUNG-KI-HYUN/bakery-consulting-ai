# FRAMEONE Feature Reverse Engineering

기준일: 2026-09-02  
방법: 경쟁사별 명칭이 달라도 동일 질문을 푸는 기능을 하나의 **기능 원자**로 정규화했다. 아래 30개 원자가 조사대상 서비스의 공개 기능과 FRAMEONE 추가 후보를 포괄한다.

판정: A 지금 독자 구현 / B 추가 API·적재 후 / C 구현 가능하나 정확도 제한 / D 유료 민간데이터 필요 / E 현재 비권장.

## F01. 주소검색·후보지 Marker

| 항목 | 내용 |
|---|---|
| 경쟁사 | OPENUP, NICE비즈맵, 마이프차, 서울, 경기도, 부동산플래닛 |
| 기능명 | 주소·건물 검색 → 후보점포 marker |
| 고객에게 주는 가치 | 상담 시작점을 실제 계약 후보에 고정 |
| 이 기능이 해결하는 질문 | “어느 점포를 분석하는가?” |

| 분석 단위 | 주소·건물·점 |
| 필요한 원천 데이터 | 도로명/지번, VWorld 등 geocoder, 기존 candidateStore |
| 필요한 계산식/통계 | 주소 정규화, geocode confidence, 중복 후보 판정 |
| 필요한 공간분석 | point 생성, 행정동·상권 point-in-polygon |
| 필요한 AI | 불필요; 주소 오류 설명 보조만 |
| FRAMEONE 구현 가능 여부 | **A**, 기존 기능 재사용 |
| 공공데이터만으로 가능한가 | 예 |
| 민간데이터가 필요한가 | 아니오 |
| 자체 DB로 가능한가 | candidateStore에 이미 존재/개발중 |
| 구현 난이도 | 낮음 |
| 데이터 신뢰도 | 높음, geocode 실패·복합건물 예외 |
| 예상 한계 | 동일 건물 내 호·층, 출입구 위치는 주소점과 다름 |
| 베이커리 창업에 필요한가 | 필수 |
| 현재 프로그램과 중복 여부 | 높음—새로 만들지 않고 확장 |
| 개발 우선순위 | 기존/P0 품질보강 |

| 데이터 신뢰도 | 자가 입력·생존자 편향·누락 관리 필요 |

| 개발 우선순위 | P2 수집, P3 분석 |
